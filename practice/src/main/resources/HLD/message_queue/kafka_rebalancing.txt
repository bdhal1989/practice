Kafka Rebalancing (Easy Notes)

🧠 1. What is Rebalancing?
👉 Rebalancing = Kafka redistributes partitions among consumers in a group
💬
“When consumers join or leave, Kafka reassigns partitions.”

🎯 2. Why Rebalancing is Needed?
👉 Because assignments can change:

✅ New consumer joins
❌ Consumer leaves/crashes
📊 Partitions increase
🔄 Consumer restarts


📦 3. Initial Setup (Before Rebalancing)
Topic: Orders

Partitions:
P0      P1      P2


👥 Consumer Group A
C1 → P0
C2 → P1
C3 → P2

✅ Balanced system

🔄 4. Scenario: New Consumer Joins
👉 New consumer C4 joins

❗ Before Rebalance
C1 → P0
C2 → P1
C3 → P2
C4 → (no partition 😴)


🔄 Rebalancing Happens
👉 Kafka redistributes partitions

✅ After Rebalance
C1 → P0
C2 → P1
C3 → P2
C4 → (still idle, no extra partitions)

👉 In this case, no change (since partitions < consumers)

🔄 Better Example (More Useful)

Before
Partitions: P0 P1 P2 P3

Consumers:
C1 → P0, P1
C2 → P2, P3


New Consumer Joins → C3

After Rebalance
C1 → P0
C2 → P1
C3 → P2, P3

✅ Load is redistributed

🚨 5. What Happens During Rebalancing? (VERY IMPORTANT 🔥)

Step-by-Step
1. All consumers STOP consuming ⛔
2. Kafka removes old partition assignments
3. Kafka assigns partitions again
4. Consumers resume ✅


⚠️ Problem: "Stop-the-World"
👉 During rebalancing:
NO consumption happens ❌

👉 Result:

Lag increases 📈
Temporary slowdown


🧠 6. Offset During Rebalancing
👉 OFFSETS are safe ✅

Example:
Before:

C1 → P0
Offset = 2


After Rebalance:
C2 → now P0


What happens?
👉 C2 continues from:
Offset = 3 ✅


✅ No data loss
✅ No reprocessing

🔁 7. Consumer Leave / Crash Scenario

Before
C1 → P0
C2 → P1


C1 crashes 💥

After Rebalance
C2 → P1, P0


✅ C2 takes over P0
✅ Continues from stored offset

📊 8. Visual Diagram
Before:

   P0      P1      P2
   │       │       │
   ▼       ▼       ▼
  C1      C2      C3


After Rebalance:

   P0      P1      P2
   │       │       │
   ▼       ▼       ▼
  C1      C3      C2


⚡ 9. Types of Rebalancing

❌ Eager Rebalance (Old)

All consumers stop ❌
All partitions reassigned ❌

👉 Heavy disruption

✅ Cooperative Rebalance (Modern 🔥)

Only required partitions move ✅
Some consumers continue working ✅

👉 Less impact

📌 10. Who Manages Rebalancing?
👉 Kafka uses:
Group Coordinator

👉 It:

Tracks consumers
Assigns partitions
Triggers rebalance


🔥 11. Key Rules
✅ Happens only within a consumer group
✅ Ensures balanced load
✅ Each partition still → 1 consumer

🧠 12. Memory Trick
👉 Think:
Team members reshuffling work


Someone joins → redistribute
Someone leaves → others pick work


🚀 13. Final Summary Diagram
               Consumer Group A

Before:

C2 → P2, P3

After New Consumer C3:

C1 → P0
C2 → P1
C3 → P2, P3


🔥 14. Key Takeaways
✅ Rebalancing = partition redistribution
✅ Triggered by consumer changes
✅ Causes temporary pause
✅ Offsets ensure safe resume
✅ Improves load balancing

💬

How to avoid rebalancing

 Why Frequent Rebalancing is a Problem?
👉 Every rebalance causes:

⛔ Consumers stop temporarily
📈 Lag increases
⚡ Performance drops


🎯 Goal
👉 Avoid unnecessary rebalancing

🧠 1. When does Rebalancing happen?
👉 Trigger conditions:
✅ Consumer joins
✅ Consumer leaves/crashes
✅ Consumer restarts
✅ Session timeout / heartbeat failure


✅ 2. How to Avoid Frequent Rebalancing

✅ ✅ 1. Use Stable Consumers (MOST IMPORTANT 🔥)
👉 Avoid frequent restarts

❌ Bad
Consumer keeps restarting every few seconds
→ Constant rebalance ❌


✅ Good
Long-running stable consumers ✅


✅ ✅ 2. Increase Session Timeout
👉 Kafka thinks consumer died if no heartbeat

Problem
Consumer slow → heartbeat delayed
Kafka thinks it died → rebalance ❌


Solution
Increase:
session.timeout.ms

✅ Gives more time before declaring failure

✅ ✅ 3. Tune Heartbeat Interval
👉 Controls how often consumer signals it's alive

Good Practice
heartbeat.interval.ms < session.timeout.ms

✅ Keeps connection healthy

✅ ✅ 4. Avoid Long Processing Inside Consumer

❌ Problem
Consumer:
Read message →
Long DB/API call (slow)
→ heartbeat delayed
→ rebalance triggered ❌


✅ Solution

Process async ✅
Use worker threads ✅
Acknowledge quickly ✅


✅ ✅ 5. Increase max.poll.interval.ms

Problem
Consumer takes too long to process batch
Kafka thinks it's dead ❌


Solution
Increase:
max.poll.interval.ms

✅ Prevents unnecessary rebalance

✅ ✅ 6. Use Static Membership (VERY IMPORTANT 🔥)

👉 Set:
group.instance.id


Without static membership
Consumer restart
→ new identity
→ rebalance ❌


With static membership ✅
Consumer restart
→ same identity
→ NO rebalance ✅


✅ ✅ 7. Use Cooperative Rebalancing

👉 Instead of full stop:
partition.assignment.strategy = cooperative


Benefits
✅ Partial reassignment
✅ Some consumers continue working
✅ Less disruption

✅ ✅ 8. Avoid Frequent Scaling Up/Down

❌ Bad
Auto-scale every few seconds
→ consumers added/removed
→ constant rebalance ❌


✅ Good
Stable scaling policies ✅


✅ ✅ 9. Proper Partition Count

❌ Too few partitions
Scaling requires changes
→ rebalance frequent ❌


✅ Good
Enough partitions for expected load ✅


📊 3. Full Strategy Diagram
        Problem: Frequent Rebalancing

   Consumer Restarts   Slow Processing   Scaling Changes
           │                 │               │
           └──────┬──────────┴──────────────┘
                  ▼
           Frequent Rebalance ❌
                  ▼
           Lag Increase 📈
                  ▼
           Performance Drop ❌


        Solution ✅

   Stable Consumers
   + Proper Timeouts
   + Static Membership
   + Cooperative Rebalancing
   + Optimized Processing


🔥 4. Golden Best Practices
✅ Use static membership
✅ Keep consumers stable
✅ Tune timeouts properly
✅ Avoid long blocking tasks
✅ Use cooperative rebalancing
✅ Avoid aggressive auto-scaling



 Kafka Rebalancing Types
There are 2 types:
1. Eager Rebalancing (Old)
2. Cooperative Rebalancing (New / Optimized)


🧠 1. Eager Rebalancing (Simple but Costly)

✅ What happens?
👉 During rebalance:
ALL consumers STOP ❌
ALL partitions are revoked ❌
Reassignment happens ❌
Then consumers resume ✅


📊 Flow
Before:
C1 → P0, P1
C2 → P2, P3


Rebalance Trigger (new consumer joins)
Step 1:
C1, C2 STOP consuming ⛔

Step 2:
All partitions removed

Step 3:
Partitions reassigned

Step 4:
All consumers start again ✅


❗ After Rebalance
C1 → P0
C2 → P1
C3 → P2, P3


🚨 Problem
NO consumption during rebalance ❌

👉 Leads to:

Lag spike 📈
Performance drop ⚠️


📉 Diagram (Eager)
Time →
------------------------------------------------
Consume   STOP   STOP   STOP   Resume
------------------------------------------------


✅ 2. Cooperative Rebalancing (Modern 🔥)

✅ What happens?
👉 Only required partitions are moved
✅ Some consumers keep working
✅ No full stop

📊 Flow
Before
C1 → P0, P1
C2 → P2, P3


New Consumer Joins → C3

Cooperative Rebalance
Step 1:
Only partitions to be moved are revoked

Step 2:
Other partitions continue processing ✅

Step 3:
Gradual reassignment


✅ After
C1 → P0
C2 → P1
C3 → P2, P3


📉 Diagram (Cooperative)
Time →
------------------------------------------------
Consume   Partial Work   Continue   Continue
------------------------------------------------

✅ No full stop
✅ Minimal disruption

🔥 Key Difference (Core Idea)

❌ Eager
All stop → all reassign → resume


✅ Cooperative
Some continue → partial reassignment


📊 Side-by-Side Comparison

🚨 Eager Rebalance

All consumers stop ❌
All partitions revoked ❌
Full reassignment ❌
High latency ⚠️
Simple ✅


✅ Cooperative Rebalance

Partial stop ✅
Only needed partitions moved ✅
Gradual reassignment ✅
Low latency ✅
More complex ⚠️


🧠 Example Visualization

Eager
C1 → P0, P1
C2 → P2, P3

Rebalance:

C1 → STOP ❌
C2 → STOP ❌

Reassign:

C1 → P0
C2 → P1
C3 → P2, P3


Cooperative
C1 → P0, P1
C2 → P2, P3

Rebalance:

Keep working:
C1 → P0 ✅
C2 → P3 ✅

Move gradually:
C3 gets P2


⚙️ How to Enable Cooperative Rebalancing
👉 Set config:
partition.assignment.strategy = cooperative-sticky


🎯 When to Use What?

✅ Use Cooperative (Recommended ✅)

Production systems
High throughput systems
Low latency requirement


❌ Eager (default in older Kafka)

Simple systems
Less sensitive workloads


🔥 Final Takeaways
✅ Eager = full stop, high disruption
✅ Cooperative = partial movement, low disruption
✅ Cooperative is preferred in modern Kafka

💬
“Eager rebalancing pauses all consumers and reassigns all partitions, whereas cooperative rebalancing performs incremental partition reassignment, allowing some consumers to continue processing and reducing disruption.”

Let’s explain how Kafka decides which consumer stops (or gives up partitions) during cooperative rebalancing in a clear, step-by-step + diagram way.

🧠 Core Idea First (VERY IMPORTANT 🔥)
👉 In cooperative rebalancing:

NOT all consumers stop ❌  
ONLY consumers owning partitions that need to move are affected ✅
✅ Others KEEP consuming

🎯 Goal of Cooperative Rebalance
👉 Minimize movement + minimize disruption

Move only what is necessary
🧩 Step-by-Step Example
✅ Initial State
Partitions:  P0   P1   P2   P3

Consumers:
C1 → P0, P1
C2 → P2, P3
➕ New Consumer Joins → C3
👉 Now Kafka needs to rebalance

🧠 Step 1: Desired Balanced State
Kafka computes:

C1 → P0
C2 → P1
C3 → P2, P3
🧠 Step 2: Identify What Needs to Move
Compare:

Current vs Desired
Partition	Current Owner	New Owner	Move?
P0				C1				C1		❌ No
P1				C1				C2		✅ Yes
P2				C2				C3		✅ Yes
P3				C2				C3		✅ Yes
✅ Step 3: Who Needs to STOP (Give Up Partitions)?
👉 Only consumers that hold partitions that must be moved

So:
C1 must give up P1 ✅
C2 must give up P2, P3 ✅
👉 These consumers partially stop (only for those partitions)

🚨 Important Insight
C1 keeps consuming P0 ✅
C2 might still consume remaining partitions (if any)
👉 They do NOT fully stop

Partition Assignment Strategy

⚙️ What Coordinator Does
👉 Kafka Group Coordinator:

Gets list of consumers
Gets partitions
Calculates optimal distribution
Compares current vs new assignment
Decides:
Which partitions stay
Which partitions move
Which consumers release partitions
🔥 MAIN RULE
Consumer stops ONLY if it needs to GIVE UP a partition
✅ Not all consumers stop
✅ Only affected ones

💡 Simple Analogy

✅ No full pause
✅ Less lag spike
✅ Faster rebalance
✅ Better throughput

ALL consumers STOP

✅ Cooperative
Only necessary partitions move
Others continue working
🔥 Final Key Takeaways
✅ Kafka computes new assignment
✅ Compares with current assignment
✅ Moves only required partitions
✅ Only those consumers stop who own those partitions
✅ Others continue

Kafka uses a partition assignment strategy (like Cooperative Sticky Assignor) to balance load evenly across consumers while minimizing partition movement.

🧠 Step-by-Step Explanation
✅ Step 1: Inputs Kafka Has
Kafka knows:

Partitions = P0, P1, P2, P3  → total 4
Consumers = C1, C2, C3       → total 3
✅ Step 2: Goal of Kafka

1. Distribute partitions evenly ⚖️
2. Avoid too much movement 🔄
✅ Step 3: Ideal Distribution
Total partitions = 4
Total consumers = 3

👉 Ideal:

Each consumer should get ~ (4 / 3 ≈ 1 or 2 partitions)
✅ Step 4: Balanced Assignment
Possible distribution:

C1 → 1 partition
C2 → 1 partition
C3 → 2 partitions
👉 That matches:

C1 → P0
C2 → P1
C3 → P2, P3 ✅
✅ Step 5: Why THIS exact mapping?
Kafka also tries to minimize movement

Previous State:
C1 → P0, P1
C2 → P2, P3
New Consumer: C3 joins
Kafka adjusts:

Move minimum partitions from existing consumers
What it does:
C1 keeps P0 ✅
C2 keeps minimal load shift ✅
C3 gets new work ✅
👉 So final:

C1 → P0
C2 → P1
C3 → P2, P3

✅ Rule 1: Balance Load
Try equal partitions per consumer
✅ Rule 2: Minimize Movement (IMPORTANT 🔥)
Don't reshuffle everything
Move only necessary partitions
✅ Rule 3: Stickiness
👉 Kafka prefers:

Keep partitions with same consumer if possible
🧠 This is called:
👉 Sticky Partition Assignment
