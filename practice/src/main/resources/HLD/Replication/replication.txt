📦 Replication in Distributed Systems (HLD)

✅ What is Replication?
Replication means storing copies of the same data across multiple machines/nodes to improve:
- ⚡ Availability
- 🚀 Read performance
- 🛡️ Fault tolerance
- 📉 Latency (geo-distribution)

🎯 Why Replication?

| ✅ Goal            | 💡 Explanation                                  |
|------------------|-----------------------------------------------|
| High Availability | System continues working even if nodes fail   |
| Fault Tolerance   | Data not lost if one server goes down         |
| Read Scalability  | Multiple replicas can serve read requests     |
| Low Latency       | Serve users from nearest replica              |
| Disaster Recovery | Backup copies prevent catastrophic loss       |

🔁 Types of Replication

1. Synchronous Replication
Write must be confirmed by replicas before success

| ✅ Pros             | ❌ Cons              |
|--------------------|---------------------|
| Strong consistency | High latency        |
| No data loss       | Lower throughput    |

2. Asynchronous Replication
Primary returns success before replicas sync

| ✅ Pros         | ❌ Cons               |
|----------------|---------------------|
| Fast writes     | Possible data loss  |
| High throughput | Eventual consistency|

3. Semi-Synchronous Replication
Hybrid approach

🏗️ Replication Architectures

1. Leader-Follower
One leader handles writes, replicas handle reads

| ✅ Pros                        | ❌ Cons              |
|------------------------------|---------------------|
| Simple design                | Leader bottleneck   |
| Strong consistency (optional)| Failover complexity |

2. Multi-Leader
Multiple nodes accept writes

| ✅ Pros           | ❌ Cons                     |
|------------------|---------------------------|
| High availability | Conflict resolution needed|
| Geo distribution  | Complex design            |

3. Leaderless
Client writes to multiple nodes

| ✅ Pros                    | ❌ Cons               |
|---------------------------|----------------------|
| Highly available          | Complex consistency  |
| No single point of failure| Read repair overhead |

⚖️ Consistency Models

| 🔄 Model              | 💡 Meaning                     |
|----------------------|-------------------------------|
| Strong Consistency   | Always latest value            |
| Eventual Consistency | Becomes consistent over time  |
| Read-After-Write     | User sees own write           |
| Causal Consistency   | Maintains order               |

🧠 Key Concepts

Quorum Rule:
W + R > N

| Symbol | Meaning        |
|--------|----------------|
| N      | Total nodes    |
| W      | Write quorum   |
| R      | Read quorum    |

Split Brain: Multiple leaders due to partition

Conflict Resolution:
- Last Write Wins
- Vector Clocks
- CRDT

📊 Comparison

| Feature     | Leader-Follower | Multi-Leader | Leaderless |
|-------------|----------------|--------------|------------|
| Write Node  | Single         | Multiple     | Any        |
| Complexity  | Low            | Medium       | High       |
| Availability| Medium         | High         | Very High  |
| Consistency | Strong/Eventual| Eventual     | Tunable    |

🚀 Use Cases

| Scenario            | Choice                     |
|---------------------|----------------------------|
| Banking            | Sync Leader-Follower        |
| Social Media       | Async Leader-Follower       |
| Global Apps        | Multi-Leader                |
| Large Scale NoSQL  | Leaderless                  |



====================================
🧠 1. CAP THEOREM (Very Important)
====================================



CAP theorem says that during a network failure (partition), a distributed system must choose between consistency and availability — it cannot provide both at the same time.


| 🔤 Property                 | 💡 Meaning                                         |
| --------------------------- | -------------------------------------------------- |
| **C – Consistency**         | Every read gets the latest correct data            |
| **A – Availability**        | Every request gets a response (even if not latest) |
| **P – Partition Tolerance** | System continues working despite network failures  |










👉 System can provide ONLY 2 out of 3:

      ┌───────────────┐
      │ Consistency   │ ✅ Same data everywhere
      └──────┬────────┘
             │
             │ choose 2
             │
┌────────────▼────────────┐
│ Availability           │ ✅ Always responds
└────────────┬───────────┘
             │
             │
      ┌──────▼────────┐
      │ Partition     │ ✅ Network failure happens
      └───────────────┘

😊 Simple meaning:
- C = Correct data
- A = System always up
- P = Network may break

🚀 KEY RULE:
👉 When network fails (Partition), choose:
   ✔ Consistency (CP system)
   ✔ OR Availability (AP system)

------------------------------------
📌 Examples:
- 💳 Banking → Consistency (Correct balance)
- 📸 Instagram → Availability (App should not fail)

====================================
⚖️ 2. LATENCY vs CONSISTENCY
====================================

🎯 Trade-off = SPEED vs CORRECTNESS

        FAST ⚡
Client ───────────────► Server
      (Low latency)
             ❌ Might get old data

        SLOW ⏱️
Client ───────────────► All replicas
      (Wait for sync)
             ✅ Always correct data

------------------------------------
📊 Summary:

| Choice          | Result                         |
|----------------|--------------------------------|
| Fast response  | Might be stale data            |
| Strong accuracy| Slight delay                   |

------------------------------------
📌 Examples:

- ❤️ Likes on Instagram → fast but may delay
- 💰 Payment → slow but accurate

💡 Interview line:
"We trade latency for consistency based on system requirements"

====================================
🔄 3. FAILURE HANDLING (FAILOVER)
====================================

👉 What happens when system crashes?

NORMAL FLOW:

Client → Leader ✅ → Replicas

FAILURE:

Client → Leader ❌ (crashed)
                 ↓
          Replica becomes Leader ✅

------------------------------------
🎯 Diagram:

Before Failure:

     Client
        │
        ▼
   🟢 Leader (Primary)
        │
   ┌────┴────┐
   ▼         ▼
Replica1   Replica2

After Failure:

     Client
        │
        ▼
   🔴 Leader (Down)
        │
   ┌────┴────┐
   ▼         ▼
🟢 New Leader Replica1   Replica2

------------------------------------
📊 Types of Failover:

| Type       | Meaning                    |
|-----------|----------------------------|
| Manual     | Human fixes it             |
| Automatic  | System auto switches ✅     |

------------------------------------
💡 Real-world analogy:
- 🎤 Main speaker fails → backup speaker takes over

====================================
🎯 FINAL INTERVIEW SUMMARY (1 MINUTE)
====================================

✅ CAP Theorem:
- Cannot have all 3 → choose between consistency and availability during failures

✅ Latency vs Consistency:
- Fast systems may return stale data
- Strong consistency systems are slower

✅ Failover:
- System automatically switches to backup when node fails
