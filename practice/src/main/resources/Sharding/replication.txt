 Replication in Sharding
This is final core concept to complete your sharding understanding.

✅ ✅ 1. What is Replication?
👉 Replication = storing copies of same data on multiple servers

✅ Simple Idea
Shard-1 (Primary)
   ↓
Replica-1
   ↓
Replica-2

👉 Same data is copied to replicas

✅ ✅ 2. Why Replication is Needed
✅ Problem without replication:
Shard-1 crashes ❌ → data lost → system down ❌


✅ With replication:
Shard-1 fails ❌
→ Replica becomes primary ✅
→ system continues ✅


✅ ✅ 3. Combining Sharding + Replication
👉 Real systems use both:
           Shard-1            Shard-2            Shard-3
         -----------        -----------        -----------
         Primary DB         Primary DB         Primary DB
             ↓                  ↓                  ↓
          Replica-1          Replica-1          Replica-1
             ↓                  ↓                  ↓
          Replica-2          Replica-2          Replica-2


✅ ✅ 4. How Requests Work

✅ Write Flow
Client → Primary Shard → Replicas

👉 Example:
Create user → goes to Shard-1 Primary
→ data copied to replicas


✅ Read Flow
Client → (Primary OR Replicas)

👉 Usually:

Reads → Replicas ✅
Writes → Primary ✅


✅ ✅ 5. Types of Replication

🔴 1. Synchronous Replication
Write → Primary → Wait for replicas → Success

✅ Strong consistency
❌ Slower

🟢 2. Asynchronous Replication (Most Common)
Write → Primary (instant)
→ Replicas updated later

✅ Fast
❌ Slight data lag (eventual consistency)

✅ ✅ 6. Important Concept: Read Scaling
👉 With replicas:
1 primary → multiple replicas

✅ You can handle:
Many read requests ✅
Less load on primary ✅


✅ ✅ 7. Failover (VERY IMPORTANT)
👉 When primary fails:
Replica becomes new Primary


✅ Flow
Primary crashes ❌
→ Replica-1 promoted ✅
→ system continues ✅


✅ ✅ 8. Problem: Data Lag ⚠️
In async replication:
Write → Primary
Immediately read → Replica → old data ❌


✅ Solution

Read from primary (critical cases)
Accept eventual consistency

✅ ✅ 12. COPY NOTES (Final)
Replication = storing multiple copies of same data

Why:
- High availability
- Fault tolerance
- Read scaling

Architecture:
Primary → Replicas

Write Flow:
Client → Primary → Replicas

Read Flow:
Client → Replicas (mostly)

Types:
1. Synchronous → consistent but slow
2. Asynchronous → fast but slight lag

Benefits:
- System doesn't fail if DB crashes
- Handles high read traffic

Problem:
- Data inconsistency (lag)

Solution:
- Read from primary (critical cases)
- Eventual consistency

Combined with Sharding:
- Sharding = distribute data
- Replication = duplicate data




What is Data Lag (Replica Lag)?
👉 In asynchronous replication:
Write → Primary (instant)
Replicas update AFTER some delay

👉 So replicas may have old data temporarily

✅ ✅ Step-by-Step Example (Very Clear)

🟢 Step 1: Write happens
User updates profile name = "Bikash"
→ goes to Primary ✅


🟢 Step 2: Replica NOT updated yet
Primary → "Bikash" ✅
Replica → still "Old Name" ❌


🟢 Step 3: Immediate Read (Problem)
Client reads from Replica
→ gets OLD value ❌


✅ ✅ Timeline View (Important)
Time T1:
Write → Primary ✅

Time T2:
Read → Replica ❌ (not updated yet)

Time T3:
Replication catches up ✅

Time T4:
Read → Replica ✅ (correct data)


✅ ✅ Visual Diagram
          WRITE
Client ─────────▶ Primary DB
                    |
                    |  (delay ⏳)
                    ▼
                Replica DB

          READ
Client ─────────▶ Replica DB ❌ (old data)


✅ ✅ Why This Happens?
👉 Because replication is:
ASYNC (not instant)

Primary:

Processes write immediately ✅

Replica:

Updates later (milliseconds / seconds delay)


✅ ✅ Real Example (Instagram / Amazon Style)
User places order ✅
→ stored in Primary

Immediately:
User checks "My Orders"
→ request goes to Replica

👉 Order NOT visible yet ❌


✅ ✅ This is Called
Eventual Consistency

👉 Data becomes correct eventually, not instantly

✅ ✅ When is This Problem Critical?
🔴 Critical Cases:

Payments
Bank balance
Order confirmation


🟢 Non-Critical Cases:

Likes count 👍
View count 👀
Social feeds


✅ ✅ Solutions (VERY IMPORTANT 🔥)

✅ 1. Read from Primary (Strong Consistency)
👉 For important data:
Read → Primary ✅

✅ Always correct
❌ Higher load on primary

✅ 2. Read-After-Write Consistency
👉 After write:
Same user → read from primary for some time

Used in:

Amazon cart
Profile updates


✅ 3. Delay Reads Slightly
Wait 100–500 ms

✅ Replica catches up

✅ 4. Use Cache (Smart Fix)
WRITE → Primary
→ also update cache

READ → Cache ✅ (latest data)


✅ 5. Accept Eventual Consistency
👉 For non-critical data:
Temporary inconsistency is OK ✅


✅ ✅ Final Summary (Copy Notes)
Data Lag (Replica Lag):

In async replication:
- Write happens in Primary instantly
- Replicas update after delay

Problem:
- Immediate read from replica returns stale data

Example:
Write → Primary
Read → Replica → old value

Solutions:
1. Read from Primary (critical cases)
2. Read-after-write consistency
3. Delay reads slightly
4. Use caching
5. Accept eventual consistency

Key Concept:
Eventual Consistency = data becomes correct after some time


✅ ✅ Interview Answer
👉 If asked:
“What is replica lag and how do you handle it?”
✅ Answer:

“Replica lag occurs in asynchronous replication when replicas are not updated immediately after a write to the primary, leading to stale reads. This can be handled by reading from the primary for critical operations, implementing read-after-write consistency, or using caching to serve the latest data.”
