=================================================
📘 STRATEGY PATTERN - COMPLETE NOTES
=================================================

CATEGORY

Behavioral Design Pattern

=================================================
DEFINITION
=================================================

Strategy Pattern is a Behavioral Design Pattern
that defines a family of algorithms,
encapsulates each algorithm, and allows them
to be selected at runtime.

Simple Rule:

Strategy = Change Behavior Dynamically

OR

Strategy = Interchangeable Algorithms

=================================================
WHY DO WE NEED IT?
=================================================

Suppose an application supports:

✔ UPI Payment

✔ Credit Card Payment

✔ PayPal Payment

-------------------------------------------------

WITHOUT STRATEGY

if(type.equals("UPI")) {

}

else if(type.equals("CARD")) {

}

else if(type.equals("PAYPAL")) {

}

-------------------------------------------------

Problems

❌ Huge if-else blocks

❌ Difficult to extend

❌ Violates Open Closed Principle

❌ Difficult to maintain

-------------------------------------------------

WITH STRATEGY

PaymentStrategy
      |
-------------------------
|          |            |
UPI      CARD       PAYPAL

Client chooses strategy
at runtime.

=================================================
CORE IDEA
=================================================

Same Task

Different Algorithms

Choose Algorithm At Runtime

EXAMPLE 1 - PAYMENT SYSTEM
=================================================

SCENARIO

Payment Can Be Made By:

✔ UPI

✔ Credit Card

✔ PayPal

-------------------------------------------------
IMPLEMENTATION MAPPING
-------------------------------------------------

Context

PaymentService

---------------------------------

Strategy

PaymentStrategy

---------------------------------

Concrete Strategies

UpiPayment

CardPayment

PaypalPayment

-------------------------------------------------
JAVA IMPLEMENTATION
-------------------------------------------------

interface PaymentStrategy {

    void pay(
            double amount);
}

-------------------------------------------------

class UpiPayment
implements PaymentStrategy {

    @Override
    public void pay(
            double amount) {

        System.out.println(
            "UPI Payment : "
            + amount);
    }
}

-------------------------------------------------

class CardPayment
implements PaymentStrategy {

    @Override
    public void pay(
            double amount) {

        System.out.println(
            "Card Payment : "
            + amount);
    }
}

-------------------------------------------------

class PaypalPayment
implements PaymentStrategy {

    @Override
    public void pay(
            double amount) {

        System.out.println(
            "Paypal Payment : "
            + amount);
    }
}

-------------------------------------------------

class PaymentService {

    private PaymentStrategy
            strategy;

    public PaymentService(
            PaymentStrategy strategy) {

        this.strategy = strategy;
    }

    public void processPayment(
            double amount) {

        strategy.pay(amount);
    }
}

-------------------------------------------------

USAGE

PaymentService service =
    new PaymentService(
        new UpiPayment());

service.processPayment(1000);

=================================================
COMMON TEMPLATE
=================================================

Strategy Interface

interface Strategy {

    void execute();
}

-------------------------------------------------

Concrete Strategy A

class StrategyA
implements Strategy {

    @Override
    public void execute() {

        System.out.println(
            "Algorithm A");
    }
}

-------------------------------------------------

Concrete Strategy B

class StrategyB
implements Strategy {

    @Override
    public void execute() {

        System.out.println(
            "Algorithm B");
    }
}

-------------------------------------------------

Context

class Context {

    private Strategy strategy;

    public Context(
            Strategy strategy) {

        this.strategy = strategy;
    }

    public void perform() {

        strategy.execute();
    }
}

=================================================
ADVANTAGES
=================================================

✔ Eliminates Large if-else Blocks

✔ Easy To Add New Algorithms

✔ Follows Open Closed Principle

✔ Runtime Behavior Change

✔ Cleaner Code

✔ Better Maintainability

=================================================
DISADVANTAGES
=================================================

❌ More Classes

❌ Client Must Know Strategy

❌ Slight Complexity Increase

=================================================
WHEN TO USE
=================================================

Use Strategy When:

✔ Multiple Algorithms Exist

✔ Behavior Changes At Runtime

✔ Large if-else Blocks Exist

Examples:

Payment Methods

Notification Channels

Sorting Algorithms

Navigation Systems

Authentication Methods

=================================================
WHEN NOT TO USE
=================================================

Single Algorithm Exists

No Runtime Change Needed

Simple Logic

=================================================
SOLID PRINCIPLES USED
=================================================

✅ OCP

Add New Strategies
Without Changing Existing Code.

---------------------------------

✅ DIP

Context Depends On Strategy
Interface.

Not Concrete Classes.

=================================================
STRATEGY vs STATE
=================================================

STRATEGY

User Selects Algorithm

Example:

UPI

CARD

PAYPAL

---------------------------------

STATE

Object Changes Behavior
Based On Internal State

Example:

Order

NEW

PAID

DELIVERED

=================================================
STRATEGY vs COMMAND
=================================================

STRATEGY

Represents Algorithm

Example:

Payment Method

---------------------------------

COMMAND

Represents Request

Example:

Place Order

Delete File

Strategy Pattern is a Behavioral Design Pattern
that defines a family of algorithms, encapsulates
each algorithm, and makes them interchangeable.
It allows the behavior of an object to change
dynamically at runtime without modifying the
client code.
