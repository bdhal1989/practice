=================================================
📘 ADAPTER PATTERN - COMPLETE NOTES
=================================================

CATEGORY

Structural Design Pattern

=================================================
DEFINITION
=================================================

Adapter Pattern is a Structural Design Pattern
that allows two incompatible interfaces to
work together.

It acts as a translator between two systems.

Simple Rule:

Adapter = Convert Interface

OR

Adapter = Translator

=================================================
WHY DO WE NEED IT?
=================================================

Suppose:

Our Application expects:

pay()

But Third Party API provides:

makePayment()

Interfaces are incompatible.

Application cannot directly use
the Third Party API.

-------------------------------------------------

Problem:

Application
      |
      X
      |
Third Party Library

-------------------------------------------------

Solution:

Application
      |
      v
Adapter
      |
      v
Third Party Library

=================================================
CORE IDEA
=================================================

Client talks to Adapter.

Adapter talks to Existing System.

Adapter converts one interface
into another.

=================================================
COMPONENTS
=================================================

1. Client

Uses Target Interface.

---------------------------------

2. Target

Expected Interface.

Example:

PaymentProcessor

---------------------------------

3. Adaptee

Existing System

Example:

RazorpayGateway

---------------------------------

4. Adapter

Converts Target Interface
to Adaptee Interface.

EXAMPLE 1 - PAYMENT GATEWAY
=================================================

SCENARIO

Application expects:

pay()

Third Party API provides:

makePayment()

-------------------------------------------------
IMPLEMENTATION MAPPING
-------------------------------------------------

Client

PaymentService

---------------------------------

Target

PaymentProcessor

---------------------------------

Adaptee

RazorpayGateway

---------------------------------

Adapter

RazorpayAdapter

-------------------------------------------------
JAVA IMPLEMENTATION
-------------------------------------------------

interface PaymentProcessor {

    void pay();
}

-------------------------------------------------

class RazorpayGateway {

    public void makePayment() {

        System.out.println(
                "Payment Successful");
    }
}

-------------------------------------------------

class RazorpayAdapter
implements PaymentProcessor {

    private RazorpayGateway
            gateway =
            new RazorpayGateway();

    @Override
    public void pay() {

        gateway.makePayment();
    }
}

-------------------------------------------------

USAGE

PaymentProcessor processor =
        new RazorpayAdapter();

processor.pay();

OUTPUT

Payment Successful

=================================================
COMMON TEMPLATE
=================================================

Target Interface

interface Target {

    void request();
}

-------------------------------------------------

Existing Class

class Adaptee {

    void specificRequest() {

    }
}

-------------------------------------------------

Adapter

class Adapter
implements Target {

    private Adaptee adaptee =
            new Adaptee();

    @Override
    public void request() {

        adaptee.specificRequest();
    }
}

=================================================
ADVANTAGES
=================================================

✔ Reuses Existing Code

✔ No Changes To Legacy System

✔ Loose Coupling

✔ Easy Third Party Integration

✔ Supports Open Closed Principle

✔ Cleaner Client Code

=================================================
DISADVANTAGES
=================================================

❌ Extra Classes

❌ Additional Layer

❌ More Complexity

=================================================
WHEN TO USE
=================================================

Use Adapter When:

✔ Two Interfaces Are Incompatible

✔ Legacy Systems Must Be Reused

✔ Third Party APIs Need Integration

✔ Data Format Conversion Is Required

Examples:

Payment Gateway

Food Delivery API

XML To JSON

Printer Systems

Email Providers

=================================================
WHEN NOT TO USE
=================================================

When interfaces already match.

Example:

interface PaymentProcessor

class StripePayment
implements PaymentProcessor

No Adapter Required.

=================================================
SOLID PRINCIPLES USED
=================================================

✅ OCP

Add New Adapters Without
Changing Existing Client Code.

Example:

RazorpayAdapter

PaypalAdapter

StripeAdapter

---------------------------------

✅ DIP

Client Depends On Interface.

Not On Concrete Implementations.

=================================================
ADAPTER vs FACTORY
=================================================

FACTORY

Problem:

Which Object To Create?

Example:

Car Or Bike

---------------------------------

ADAPTER

Problem:

How To Connect Incompatible Systems?

Example:

US Charger + Indian Socket

=================================================
ADAPTER vs BRIDGE
=================================================

ADAPTER

Fixes Existing Incompatibility

Example:

pay()

makePayment()

---------------------------------

BRIDGE

Prevents Class Explosion

Example:

Remote + Device
