=================================================
📘 SINGLETON PATTERN
=================================================

📌 Intent

Ensure only ONE instance of a class exists
and provide a global access point to it.

-------------------------------------------------
🏦 REAL WORLD PROBLEM
-------------------------------------------------

Banking Application

Services:

✔ AccountService
✔ PaymentService
✔ LoanService

All need DatabaseConnection.

Without Singleton:

new DatabaseConnection();
new DatabaseConnection();
new DatabaseConnection();

Many unnecessary objects created.

-------------------------------------------------
✅ SOLUTION
-------------------------------------------------

Allow only ONE object.

-------------------------------------------------
📌 EAGER INITIALIZATION
-------------------------------------------------

Definition:

Object is created immediately when
class is loaded.

✅ Complete Example

class DatabaseConnection {

    private static final DatabaseConnection INSTANCE =
            new DatabaseConnection();

    private DatabaseConnection() {
    }

    public static DatabaseConnection getInstance() {
        return INSTANCE;
    }
}

-------------------------------------------------
USAGE
-------------------------------------------------

DatabaseConnection db1 =
    DatabaseConnection.getInstance();

DatabaseConnection db2 =
    DatabaseConnection.getInstance();

System.out.println(db1 == db2);

Output:

true

-------------------------------------------------
ADVANTAGES
-------------------------------------------------

✔ Simple

✔ Thread Safe

✔ Easy Implementation

-------------------------------------------------
DISADVANTAGES
-------------------------------------------------

❌ Object created even if never used

❌ Memory may be wasted

-------------------------------------------------
📌 LAZY INITIALIZATION
-------------------------------------------------

Definition:

Object is created only when needed.

✅ Complete Example

class DatabaseConnection {

    private static DatabaseConnection instance;

    private DatabaseConnection() {
    }

    public static DatabaseConnection getInstance() {

        if(instance == null) {
            instance =
                new DatabaseConnection();
        }

        return instance;
    }
}

-------------------------------------------------
USAGE
-------------------------------------------------

DatabaseConnection db1 =
    DatabaseConnection.getInstance();

DatabaseConnection db2 =
    DatabaseConnection.getInstance();

System.out.println(db1 == db2);

Output:

true

-------------------------------------------------
ADVANTAGES
-------------------------------------------------

✔ Memory Efficient

✔ Object created on demand

-------------------------------------------------
DISADVANTAGES
-------------------------------------------------

❌ Not Thread Safe

-------------------------------------------------
📌 THREAD SAFETY PROBLEM
-------------------------------------------------

Thread 1 calls getInstance()

Thread 2 calls getInstance()

At same time

Possible:

Thread 1 → creates Object A

Thread 2 → creates Object B

❌ Singleton broken

-------------------------------------------------
✅ THREAD SAFE VERSION
-------------------------------------------------

class DatabaseConnection {

    private static DatabaseConnection instance;

    private DatabaseConnection() {
    }

    public static synchronized
    DatabaseConnection getInstance() {

        if(instance == null) {
            instance =
                new DatabaseConnection();
        }

        return instance;
    }
}

-------------------------------------------------
ADVANTAGES
-------------------------------------------------

✔ Thread Safe

✔ Single Object Guaranteed

-------------------------------------------------
DISADVANTAGES
-------------------------------------------------

❌ Slight performance overhead

-------------------------------------------------
📌 REAL WORLD EXAMPLES
-------------------------------------------------

✔ Spring Beans (default singleton scope)

✔ Logger

✔ Configuration Manager

✔ Cache Manager

✔ Printer Manager

-------------------------------------------------
📌 WHEN TO USE
-------------------------------------------------

Use when only ONE object is needed.

Examples:

DatabaseConnection

Logger

CacheManager

ConfigurationManager

-------------------------------------------------
📌 WHEN NOT TO USE
-------------------------------------------------

Customer

Order

Book

Employee

Transaction

These require multiple objects.

-------------------------------------------------
🧠 MEMORY TRICK
-------------------------------------------------

One Country
→ One Prime Minister

One Company
→ One CEO

One Application
→ One Configuration Manager

-------------------------------------------------
🎯 INTERVIEW ANSWER
-------------------------------------------------

that ensures only one instance of a class
exists and provides a global access point
to that instance.







=================================================
📘 FACTORY METHOD PATTERN
=================================================

📌 Story

Swiggy Application

Customer orders:

Pizza
Burger
Pasta

-------------------------------------------------
📌 Problem
-------------------------------------------------

Client creates objects directly.

Food food;

if(type.equals("PIZZA")) {
    food = new Pizza();
}
else if(type.equals("BURGER")) {
    food = new Burger();
}

Problems:

❌ Tight Coupling
❌ Huge if-else chains
❌ Difficult to add new types
❌ Violates OCP

-------------------------------------------------
📌 Pattern Intent
-------------------------------------------------

Encapsulate object creation logic into
a dedicated Factory class.

Client requests objects from Factory
instead of creating them directly.

-------------------------------------------------
📌 Complete Example
-------------------------------------------------

interface Food {

    void prepare();
}

class Pizza implements Food {

    public void prepare() {
        System.out.println("Preparing Pizza");
    }
}

class Burger implements Food {

    public void prepare() {
        System.out.println("Preparing Burger");
    }
}

class Pasta implements Food {

    public void prepare() {
        System.out.println("Preparing Pasta");
    }
}

class FoodFactory {

    public static Food getFood(
            String type) {

        if(type.equals("PIZZA")) {
            return new Pizza();
        }

        if(type.equals("BURGER")) {
            return new Burger();
        }

        if(type.equals("PASTA")) {
            return new Pasta();
        }

        throw new IllegalArgumentException(
            "Invalid Food Type"
        );
    }
}

-------------------------------------------------
📌 Usage
-------------------------------------------------

Food food =
    FoodFactory.getFood("PIZZA");

food.prepare();

Output:

Preparing Pizza

-------------------------------------------------
📌 Visualization
-------------------------------------------------

Without Factory

Client
 ├── new Pizza()
 ├── new Burger()
 └── new Pasta()

-----------------------------------

With Factory

Client
   |
   v
FoodFactory
   |
   +---- Pizza
   |
   +---- Burger
   |
   +---- Pasta

-------------------------------------------------
📌 Real World Examples
-------------------------------------------------

✔ Spring ApplicationContext

✔ LoggerFactory

✔ DriverManager

✔ Payment Gateway

✔ Vehicle Factory

-------------------------------------------------
📌 Advantages
-------------------------------------------------

✔ Loose Coupling

✔ Centralized Creation Logic

✔ Better Maintainability

✔ Supports OCP

✔ Easier Testing

-------------------------------------------------
📌 Disadvantages
-------------------------------------------------

❌ More Classes

❌ Factory Can Become Large

-------------------------------------------------
📌 When To Use
-------------------------------------------------

✔ Multiple object types exist

✔ Complex creation logic

✔ Client should not know creation details

Examples:

Payment System

Notification System

Vehicle System

Food Ordering System

-------------------------------------------------
📌 When Not To Use
-------------------------------------------------

Simple object creation.

Example:

User user = new User();

No Factory needed.

-------------------------------------------------
📌 SOLID Principles Used
-------------------------------------------------

✅ OCP

New products added without changing
client logic.

✅ DIP

Client depends on abstraction
(Food interface).

-------------------------------------------------
📌 Interview Questions
-------------------------------------------------

Q. What problem does Factory solve?

Object creation complexity and
tight coupling.

-----------------------------------

Q. Difference between Factory and Singleton?

Singleton:
Controls number of objects.

Factory:
Controls object creation.

-------------------------------------------------
🧠 Memory Trick
-------------------------------------------------

Customer Orders Food

Kitchen Decides What To Create

Kitchen = Factory

-------------------------------------------------
🔥 Interview Answer
-------------------------------------------------

Factory Method Pattern provides a way
to create objects without exposing
creation logic to the client. It
centralizes object creation and
reduces coupling between client code
and concrete implementations.



=================================================
📘 ABSTRACT FACTORY PATTERN
=================================================

📌 DEFINITION

Abstract Factory is a Creational Design Pattern
that provides an interface for creating FAMILIES
of related objects without specifying their
concrete classes.

-------------------------------------------------
📌 SIMPLE UNDERSTANDING
-------------------------------------------------

Factory Pattern

Creates ONE object.

Example:

FoodFactory
    |
    └── Pizza

-----------------------------------

Abstract Factory Pattern

Creates a FAMILY of related objects.

Example:

AppleFactory
    |
    ├── iPhone
    └── MacBook

-------------------------------------------------
📌 WHEN TO USE
-------------------------------------------------

Use when:

✔ Multiple related objects must be created together

✔ Product families exist

✔ Client should not know object creation details

-------------------------------------------------
📌 STORY 1 - PAYMENT SYSTEM
-------------------------------------------------

Suppose our application supports:

1. Razorpay
2. Paypal

Each provider offers multiple payment types.

Razorpay Family

✔ Razorpay UPI
✔ Razorpay Card

Paypal Family

✔ Paypal Wallet
✔ Paypal Card

We want the client to select a provider and
get all related payment products.

-------------------------------------------------
❌ WITHOUT ABSTRACT FACTORY
-------------------------------------------------

if(provider.equals("RAZORPAY")) {

    upi = new RazorpayUpiPayment();

    card = new RazorpayCardPayment();
}
else if(provider.equals("PAYPAL")) {

    upi = new PaypalWalletPayment();

    card = new PaypalCardPayment();
}

Problems:

❌ Huge if-else

❌ Tight Coupling

❌ Difficult to add new provider

❌ Violates OCP

-------------------------------------------------
✅ SOLUTION
-------------------------------------------------

STEP 1 - Product Interfaces

interface UpiPayment {

    void pay();
}

interface CardPayment {

    void pay();
}

-------------------------------------------------
STEP 2 - Razorpay Products
-------------------------------------------------

class RazorpayUpiPayment
implements UpiPayment {

    public void pay() {

        System.out.println(
            "Razorpay UPI Payment"
        );
    }
}

class RazorpayCardPayment
implements CardPayment {

    public void pay() {

        System.out.println(
            "Razorpay Card Payment"
        );
    }
}

-------------------------------------------------
STEP 3 - Paypal Products
-------------------------------------------------

class PaypalWalletPayment
implements UpiPayment {

    public void pay() {

        System.out.println(
            "Paypal Wallet Payment"
        );
    }
}

class PaypalCardPayment
implements CardPayment {

    public void pay() {

        System.out.println(
            "Paypal Card Payment"
        );
    }
}

-------------------------------------------------
STEP 4 - Abstract Factory
-------------------------------------------------

interface PaymentFactory {

    UpiPayment createUpiPayment();

    CardPayment createCardPayment();
}

-------------------------------------------------
STEP 5 - Concrete Factories
-------------------------------------------------

class RazorpayFactory
implements PaymentFactory {

    public UpiPayment createUpiPayment() {

        return new RazorpayUpiPayment();
    }

    public CardPayment createCardPayment() {

        return new RazorpayCardPayment();
    }
}

-----------------------------------

class PaypalFactory
implements PaymentFactory {

    public UpiPayment createUpiPayment() {

        return new PaypalWalletPayment();
    }

    public CardPayment createCardPayment() {

        return new PaypalCardPayment();
    }
}

-------------------------------------------------
STEP 6 - Client Usage
-------------------------------------------------

PaymentFactory factory =
        new RazorpayFactory();

        factory.createUpiPayment();

        factory.createCardPayment();

card.pay();

📘 BUILDER PATTERN
=================================================

📌 DEFINITION

Builder Pattern is a Creational Design Pattern
used to create complex objects step-by-step.

It is useful when an object has:

✔ Many fields
✔ Optional fields
✔ Large constructors

-------------------------------------------------
📌 PROBLEM
-------------------------------------------------

Suppose we have an Employee class.

Fields:

name
email
department
salary
phone
address
manager

-------------------------------------------------
❌ WITHOUT BUILDER
-------------------------------------------------

class Employee {

    private String name;
    private String email;
    private String department;
    private double salary;
    private String phone;
    private String address;
    private String manager;

    public Employee(
        String name,
        String email,
        String department,
        double salary,
        String phone,
        String address,
        String manager) {

        this.name = name;
        this.email = email;
        this.department = department;
        this.salary = salary;
        this.phone = phone;
        this.address = address;
        this.manager = manager;
    }
}

Usage:

Employee employee =
    new Employee(
        "Bikash",
        "bikash@gmail.com",
        "Technology",
        100000,
        "9999999999",
        "Kolkata",
        "Suyash"
    );

-------------------------------------------------
🚨 PROBLEMS
-------------------------------------------------

❌ Constructor becomes huge

❌ Hard to remember parameter order

❌ Difficult to read

❌ Difficult to maintain

❌ Adding new field requires new constructor

-------------------------------------------------
✅ BUILDER SOLUTION
-------------------------------------------------

class Employee {

    private String name;
    private String email;
    private String department;
    private double salary;
    private String phone;
    private String address;
    private String manager;

    private Employee(Builder builder) {

        this.name = builder.name;
        this.email = builder.email;
        this.department = builder.department;
        this.salary = builder.salary;
        this.phone = builder.phone;
        this.address = builder.address;
        this.manager = builder.manager;
    }

    public static class Builder {

        private String name;
        private String email;
        private String department;
        private double salary;
        private String phone;
        private String address;
        private String manager;

        public Builder name(String name) {
            this.name = name;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public Builder department(
                String department) {

            this.department = department;
            return this;
        }

        public Builder salary(double salary) {

            this.salary = salary;
            return this;
        }

        public Builder phone(String phone) {

            this.phone = phone;
            return this;
        }

        public Builder address(String address) {

            this.address = address;
            return this;
        }

        public Builder manager(String manager) {

            this.manager = manager;
            return this;
        }

        public Employee build() {

            return new Employee(this);
        }
    }
}

-------------------------------------------------
✅ USAGE
-------------------------------------------------

Employee employee =
    new Employee.Builder()
        .name("Bikash")
        .email("bikash@gmail.com")
        .department("Technology")
        .salary(100000)
        .phone("9999999999")
        .address("Kolkata")
        .manager("Suyash")
        .build();

=================================================
📘 FACTORY vs BUILDER PATTERN
=================================================

Many people get confused between:

✔ Factory Pattern
✔ Builder Pattern

The easiest way to understand:

Factory = WHAT object to create

Builder = HOW to create complex object

=================================================
📌 FACTORY PATTERN
=================================================

Purpose:

Create different types of objects.

Factory decides WHICH object to create.

-------------------------------------------------
EXAMPLE
-------------------------------------------------

Vehicle vehicle =
    VehicleFactory.getVehicle("CAR");

Factory internally decides:

if(type.equals("CAR")) {
    return new Car();
}

if(type.equals("BIKE")) {
    return new Bike();
}

-------------------------------------------------
KEY IDEA
-------------------------------------------------

One request

→ One object returned

Client does not care how object is created.

=================================================
📌 BUILDER PATTERN
=================================================

Purpose:

Create a complex object step-by-step.

Builder decides HOW object is constructed.

-------------------------------------------------
EXAMPLE
-------------------------------------------------

Employee employee =
    new Employee.Builder()
        .name("Bikash")
        .email("bikash@gmail.com")
        .salary(100000)
        .department("Technology")
        .build();

-------------------------------------------------
KEY IDEA
-------------------------------------------------

Object is built gradually.

Field by field.

=================================================

=================================================

"Give me a BMW."

Showroom gives BMW.

You don't care how it was made.

-----------------------------------------

✔ Cheese

✔ Sauce

✔ Fries

✔ Coke

Factory Pattern is used to create and return
different types of objects while hiding creation
logic.

Builder Pattern is used to construct a complex
object step-by-step, especially when the object
contains many fields or optional parameters.

📘 PROTOTYPE PATTERN
=================================================

📌 DEFINITION

Prototype Pattern is a Creational Design Pattern
used to create new objects by copying (cloning)
an existing object instead of creating it from scratch.

Simple Rule:

Prototype = Copy Existing Object

-------------------------------------------------
📌 WHY DO WE NEED IT?
-------------------------------------------------

Sometimes object creation is:

✔ Expensive
✔ Time Consuming
✔ Repetitive

Instead of creating the same object again
and again using new(),

we create one object and make copies of it.

-------------------------------------------------
📌 SIMPLE REAL-LIFE EXAMPLE
-------------------------------------------------

Teacher creates:

1 Question Paper

Need:

100 Copies

Options:

❌ Write the same paper 100 times

OR

✅ Photocopy the original paper 100 times

Prototype Pattern = Photocopy Machine

-------------------------------------------------
📌 STORY
-------------------------------------------------

Suppose we are building a game.

Need:

1000 Soldiers

Every Soldier has:

✔ Gun
✔ Health = 100
✔ Power = 50
✔ Armor = Level 5

Creating each soldier from scratch is expensive.

-------------------------------------------------
❌ WITHOUT PROTOTYPE
-------------------------------------------------

Soldier s1 = new Soldier();

Soldier s2 = new Soldier();

Soldier s3 = new Soldier();

...

1000 times

Problems:

❌ Expensive Initialization

❌ Repeated Configuration

❌ Poor Performance

-------------------------------------------------
✅ WITH PROTOTYPE
-------------------------------------------------

Create one Soldier.

Soldier original =
    new Soldier();

Create copies.

Soldier s2 =
    original.clone();

    original.clone();

Converts one interface into another.

-------------------------------------------------
📌 COMPLETE EXAMPLE
-------------------------------------------------

STEP 1

Target Interface

interface PaymentProcessor {

    void pay();
}

-----------------------------

STEP 2

Existing Third Party Class

class RazorpayGateway {

    public void makePayment() {

        System.out.println(
            "Payment Successful"
        );
    }
}

-----------------------------

STEP 3

Adapter

class RazorpayAdapter
implements PaymentProcessor {

    private RazorpayGateway gateway =
            new RazorpayGateway();

    public void pay() {

        gateway.makePayment();
    }
}

-----------------------------

STEP 4

Usage

PaymentProcessor processor =
        new RazorpayAdapter();

processor.pay();

Output:

Payment Successful

📘 ADAPTER PATTERN
=================================================

📌 CATEGORY

Structural Design Pattern

-------------------------------------------------
📌 DEFINITION
-------------------------------------------------

Adapter Pattern is a Structural Design Pattern
that allows two incompatible interfaces to
work together.

It acts as a translator between two systems.

-------------------------------------------------
📌 SIMPLE UNDERSTANDING
-------------------------------------------------

System A speaks English.

System B speaks Hindi.

They cannot communicate directly.

Need:

Translator

English
    |
Translator
    |
Hindi

Translator = Adapter

📘 BRIDGE PATTERN
=================================================

📌 CATEGORY

Structural Design Pattern

-------------------------------------------------
📌 DEFINITION
-------------------------------------------------

Bridge Pattern is a Structural Design Pattern
that separates an abstraction from its
implementation so that both can evolve
independently.

Simple Rule:

Bridge = Separate Two Independent Dimensions

-------------------------------------------------
📌 WHY DO WE NEED IT?
-------------------------------------------------

Sometimes a system has two things that can
change independently.

Example:

Remote Types

✔ Basic Remote
✔ Advanced Remote

Device Types

✔ TV
✔ Radio
✔ AC

If every Remote is combined with every Device,
the number of classes increases rapidly.

-------------------------------------------------
❌ WITHOUT BRIDGE
-------------------------------------------------

BasicTVRemote

AdvancedTVRemote

BasicRadioRemote

AdvancedRadioRemote

BasicACRemote

AdvancedACRemote

Now add:

VoiceRemote

Need:

VoiceTVRemote

VoiceRadioRemote

VoiceACRemote

Classes keep increasing.

Problem:

❌ Too Many Classes

❌ Difficult To Maintain

❌ Code Duplication

❌ Class Explosion

-------------------------------------------------
✅ WITH BRIDGE
-------------------------------------------------

Separate:

Remote

and

Device

Connect both using composition.

Remote
      |
      v
Device

Now both can grow independently.

-------------------------------------------------
📌 CORE IDEA
-------------------------------------------------

Bridge Pattern is used when:

Two dimensions vary independently.

Examples:

Remote + Device

Shape + Color

Payment + Bank

Notification + Channel

Vehicle + Engine

Instead of creating a class for every
combination, separate both dimensions.

-------------------------------------------------

Suppose a company manufactures:

-------------------------------------------------
📌 COMPLETE EXAMPLE
-------------------------------------------------

STEP 1

Device Interface

interface Device {

    void on();

    void off();
}

---------------------------------

STEP 2

Concrete Devices

class TV implements Device {

    public void on() {

        System.out.println("TV ON");
    }

    public void off() {

        System.out.println("TV OFF");
    }
}

---------------------------------

class Radio implements Device {

    public void on() {

        System.out.println("Radio ON");
    }

    public void off() {

        System.out.println("Radio OFF");
    }
}

---------------------------------

STEP 3

Abstraction

abstract class Remote {

    protected Device device;

    public Remote(Device device) {

        this.device = device;
    }

    abstract void power();
}

---------------------------------

STEP 4

Refined Abstraction

class BasicRemote
extends Remote {

    public BasicRemote(Device device) {

        super(device);
    }

    public void power() {

        device.on();
    }
}

---------------------------------

STEP 5

Usage

Device tv = new TV();

Remote remote =
        new BasicRemote(tv);

remote.power();

Output:

TV ON
